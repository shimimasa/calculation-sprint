# 計算スプリント 改善コンサルティングレポート

作成日: 2026-07-16
対象: 現行本番導線(Dash Run 3モード)+ 開発計画(refactoring-plan / new-element)
調査方法: 実コード全数調査(src 51ファイル・約11,500行)、仕様書・ADR・過去レビュー・生徒フィードバック3回分の突き合わせ

---

## 0. 総評

**「走るのが楽しいゲーム」としてはよく出来ている。「計算を学ぶゲーム」としては、学習ループの後半が欠けている。**

現行のDash Runは、正解→加速→敵撃破という「解く快感」の設計が丁寧で、生徒フィードバックにも真摯に応えてきた(敵・ボス・コンボ演出はすべて生徒の要望由来)。難易度テーブル(くり上がり制御・割り切れる除算)も教育的に良質。

一方で、**「間違えたとき」に学びが発生しない**。誤答時は「×」の記号だけが表示され、正答は示されず、即座に次のランダム問題へ進む。間違えた問題の再出題も、苦手演算の記録もない。つまり現状は「できることを速く反復する装置」であり、「できないことができるようになる装置」ではない。

皮肉なことに、復習提案・苦手集計・日次統計という教育機能は**すべて実装済みだが、無効化されたレガシーコード側に孤立**している。本レポートの中心提案は「この教育資産をDashに接続し直すこと」である。

## 1. 現状の強み(変えないでよいもの)

| 領域 | 評価 | 根拠 |
|---|---|---|
| 難易度テーブル | ◎ | `dashDifficultyTable.js`: carry/borrow を avoid/some/mixed/prefer の4段階で制御。乗算Lv1は2・5・10の段(九九の学習順に整合)。除算は逆算生成で必ず割り切れ、Lv5のみ「あまり率20%」 |
| モード設計 | ◎ | `game/dash/modes/` のStrategyパターン+timePolicy契約は拡張しやすく、開発時警告まである。新モード追加コストが低い |
| 入力・アクセシビリティ | ○ | テンキー/物理キーボード両対応、Enter非依存の確定ボタン、aria属性、prefers-reduced-motion尊重 |
| 運用原則 | ◎ | 匿名プロファイル分離・比較ストレス抑制・学習達成の誤保証禁止(product-spec)。現行Dashでは「今日のTOP3」も書き込まれておらず、比較構造は事実上消えている |
| 生徒との共創 | ◎ | フィードバック3回分→敵・ボス・コンボ実装のサイクルが回っている。これ自体が最大の教育的資産 |
| 誤答ペナルティの水準 | ○ | 旧モード(9重の負刺激)と比べ、Dashは −800ms+コンボ消滅程度に軽量化済み。誤答時に敵速度が基準値へリセットされる「隠れた救済」もある |

過去のOpus 4.6レビューの指摘(摩擦・赤フラッシュ・「称号なし」等)の多くは**旧gameScreen(現在到達不能)に対するもの**で、現行Dashでは該当しないか解消済み(称号は全員がフォールバック称号を得られる)。ただし1点だけ**悪化**している: 旧モードは誤答時に正答を500ms表示していたが、Dashは**0ms(非表示)**。

## 2. 最重要課題: 「間違い→理解」のループが存在しない

`dashGameScreen.js` の `submitAnswer()`(誤答分岐, L2234-2242):

```js
audioManager.playSfx('sfx_wrong');
gameState.dash.wrongCount += 1;
gameState.dash.streak = 0;
this.enemySpeed = enemyBaseSpeed;
this.timeLeftMs += Number(this.timePolicy?.onWrongMs) || 0;  // -800ms
this.setFeedback('×', 'wrong');   // ← 正答は表示されない
...
this.loadNextQuestion();          // ← 即・次のランダム問題へ
```

これにより:

1. **正答を知る機会がない** — 「7×8を間違えた」子は、正しい答えを知らないまま次に進む。同じ誤りが定着するリスクすらある
2. **再挑戦の機会がない** — 間違えた問題は二度と(偶然を除き)出てこない
3. **苦手が記録されない** — どの演算・どのパターンで間違えたかのデータが現行モードでは一切残らない
4. **重複出題対策もない** — `questionGenerator.next()` に直近問題の記憶がなく、同じ問題が連続し得る(学習効率と「ちゃんと考えた感」の両方を損なう)

一方、レガシー側には `reviewSummary.js`(苦手演算判定+「まずは繰り上がりなしで練習しよう」等の提案文)、`dailyStatsStore` の `wrongByMode`(演算別誤答数)、復習ループ(10問)が**完成品として存在**する。

> ⚠️ **リファクタリング計画との衝突**: `spec/plan/refactoring-plan.md` Phase 1 は `reviewSummary.js` を「gameScreen専用」として削除対象に挙げている。**削除する前にDashへの移植可否を判断すべき**。少なくとも `reviewSummary.js` の提案文言と `wrongByMode` のスキーマは再利用価値が高い。

## 3. 提案ロードマップ(教育効果 × 工数)

### P1: 学習ループの最小完成(低〜中工数・効果最大)

**P1-1. 誤答時に正答を表示し、一拍おく**
- `setFeedback('×', 'wrong')` → `setFeedback(`× こたえ: ${answer}`, 'wrong')`
- 表示中1.2〜1.5秒はタイマー・敵の追走を停止(でなければ「正答を読む=損」になり本末転倒)
- 工数: 小。rAFループ内の一時停止フラグ1本で実現可能

**P1-2. 「まちがい直し」再出題(リベンジシステム)**
- 誤答した問題を2〜3問後にもう一度出題(軽いspaced repetition)
- 再挑戦で正解したら「リベンジせいこう!」演出+小ボーナス(時間 or XP)
- **間違いが「損失」から「あとで取り返せるチャンス」に変わる**。これは失敗回避傾向の子に最も効く設計変更
- 工数: 小。再出題キュー(配列1本)と正解時の分岐のみ

**P1-3. 重複出題防止**
- `questionGenerator.next()` に直近5問程度のキー(`${a}${op}${b}`)を記憶し、重複時は再抽選(既存の `maxAttempts` 機構に相乗り)
- 工数: 極小

### P2: 学習データの接続(中工数)

**P2-1. 苦手記録をDashに接続**
- 誤答時に演算別(可能ならcarry/borrowパターン別)の誤答を `dash.stats` または日次ストアに記録
- リザルト画面に「きょうのふりかえり」カード: 苦手演算+`reviewSummary.js` 由来の提案文(「九九をゆっくり確実に言えるか確認しよう」等)
- ⚠️ refactoring-plan Phase 1 の削除前に移植すること

**P2-2. 次レベルのおすすめ表示**
- リザルトで「正答率95%以上&ノーヒット → つぎはLv3にちょうせん!」のような推薦カード
- 自動で難易度を変えるのではなく**推薦に留める**(子どもの自己決定を守る。教室運用でも予測可能性が保たれる)
- 既存の `dash.stats`(ステージ別ベスト・プレイ回数)で実現可能

**P2-3. 「じっくりモード」(タイマーなし練習モード)の追加**
- timePolicy契約が既にあるため、時間切れなし・ペナルティなしの第4モードは低コストで追加できる
- product-specが掲げる「支援現場」利用に現状最も欠けているピース。時間プレッシャーが認知過負荷になる子(過去レビューの指摘)への直接的な回答になる

### P3: モチベーション軸の多様化(生徒要望との整合)

`spec/plan/new-element.md` の優先順位に「教育効果」の軸を加えると、推奨順が変わる:

| new-element項目 | 生徒要望 | 教育価値 | 推奨 |
|---|---|---|---|
| 図鑑(遭遇=登録)+レア敵 | ◎(3回目③⑦) | **◎ 速さと無関係の報酬軸**。遅い子も収集で達成感を得られる | **優先度を上げる** |
| XP/Lv(正解+1、完走+5) | ◎ | ○ ただし**減点なし・取り組み量ベース**を厳守。リベンジ成功+2など「粘り」に配点すると学習観がよくなる | 設計案のまま進めてよい |
| ボスHP・武器風演出 | ◎ | △ 楽しさ寄与のみ(それで十分価値がある) | 中 |
| 速度成長 | ○ | ✗ テンポ崩壊リスク(計画書の指摘どおり最後) | 後回し |

称号にも成長軸を追加推奨: 「ねばり屋」(リベンジ成功数)、「せいちょう株」(前回比で正答率up)、「ちょうせんしゃ」(前回より上のレベルに挑戦)。P1-2を入れると自然に実装できる。

### P4: 授業運用の視点(先生向け)

- **scoreAttack60を授業のメインに推す**: 60秒固定なので全員が同時に終わる。速い子も遅い子も「同じ時間」を使う構造は、product-specの比較ストレス抑制と整合する
- **バランス調整は教室実測後に**(new-product-spec-reviewの方針を支持)。ただし計測装置を先に入れる: `endReason` の分布・平均誤答数・プロファイル別の継続日数をログすれば、「−800msが厳しすぎるか」をデータで判断できる。現状の非対称(+500ms/−800ms)は、P1-1/P1-2導入後に再評価すればよい
- **アセット134MBは教室回線で実害**が出やすい。refactoring-plan Phase 6(→50MB目標)は独立フェーズなので前倒し可能

## 4. 進め方: リファクタリング計画との統合

refactoring-plan の「挙動変更とリファクタを混ぜない」原則は正しい。その上で:

1. **Phase 0(Playwrightスモーク+CI)を最初に** — 本レポートのP1〜P2も全て挙動変更なので、安全網の恩恵をそのまま受ける
2. **Phase 1(デッドコード削除)を修正** — `reviewSummary.js` は「削除」ではなく「`src/game/dash/` へ移植後に旧参照を削除」に変更。`dailyStatsStore` の `wrongByMode` スキーマも P2-1 の受け皿として温存
3. **P1系(正答表示・リベンジ・重複防止)は独立PRとして早期に** — Phase 4(dashGameScreen分割)を待つ必要はない。`submitAnswer()` と `questionGenerator` への局所変更で済み、むしろ分割後の `questionFlow.js` の仕様が先に固まる
4. Phase 4以降は計画書どおり
